# REG 加腿/减腿对称性测试说明

## 测试目标

验证带电中继（REG）的保护腿在增加和删除后完全对称，并保证共享 OCH、共享 REG 板卡或共享物理资源时，不删除其他 Tunnel 正在使用的正常腿资源。

测试覆盖以下资源：

- Tunnel、OCH 的路由、保护腿数、状态和临时 marker；
- SiteLink 及其 OCH 关联；
- PhyLink、ViewLink、InternalLink；
- REG 节点、TPC4 板卡、两个 REG L 口；
- 两条 REG L 口自环 XC；
- 四条双向 REG OS Link 及对应 InternalLink；
- 两侧 MUX 的 EXT/EXP XC；
- SiteNode rack 与新建 REG 物理网元的关系。

## 测试数据

- MongoDB：`mongodb://localhost:27017/sotn`
- 基线 dump：`C:\DCI\server-test\mongo-dump\sotn`
- Tunnel：

```text
Tunnel-Site-2083017033158627328#Ne-2084903014245732352#LINECARD-1-3#PORT-1-3-C3-Site-2083017032311377920#Ne-2084903014325424128#LINECARD-1-3#PORT-1-3-C3
```

测试不读取 `bind-tunnel-add-leg-with-path*.json`。它调用 `getBindingList()` 取得当前数据库中的真实候选路径，并把第一座中间站设置为 REG，避免测试输入与 YANG schema 或当前拓扑模型脱节。

当前 dump 只有一条包含中间站、可构造 REG 的候选路径。测试 third REG 时先用 direct path 构造普通 secondary，再把带中间站的路径作为 third；因此 REG 删除同时覆盖 secondary 和 third 两个位置。

## 对称循环

`TunnelBinderDoItTest#testAddRemoveRegProtectionLegResourceSymmetry` 首先把三腿基线按“third 优先、secondary 其次”减成一腿，然后保存一腿资源快照。之后连续执行三轮：

1. 增加带 REG 的 secondary。
2. 断言新增腿包含两个 REG L 口、两条 REG 自环 XC、四条方向 OS Link、四条对应 InternalLink。
3. 删除 secondary，断言数据库逐资源回到一腿快照。
4. 增加 direct secondary，保存两腿快照。
5. 增加带 REG 的 third。
6. 删除 third，断言数据库逐资源回到两腿快照。
7. 删除 direct secondary，断言数据库再次回到一腿快照。

快照读取并排序比较以下集合：

```text
config-tunnel
config-och-link
config-site-link
config-phy-link
config-phy-node
config-site-node
config-view-link
config-view-node
```

快照保留资源 ID、端口属性、XC、InternalLink、Equipment、rack 等业务字段；只归一化对象字段顺序、数组顺序以及无业务差异的 null/空容器。任何资源泄漏、Busy L 口、残留 marker、空壳板卡或节点、已有资源字段变化都会使断言失败。

## 如何用单元测试证明加减腿对称

### 对称性的判定标准

这里的“对称”不是只比较保护腿数量，而是比较整个资源状态：

```text
加腿前资源快照 S
    ↓ add-leg
产生资源增量 Δ
    ↓ remove-leg（删除刚增加的同一条腿）
最终资源快照必须严格回到 S
```

因此测试同时证明两件事：

1. 加腿新增的 REG/XC/链路/端口/板卡/节点资源全部被删除或恢复；
2. 加腿前已存在的 Tunnel、OCH、正常腿和共享资源逐字段保持不变。

如果只断言腿数从 2 变成 1，无法发现 Busy L 口、残留 XC、空壳板卡、marker 或其他 Tunnel 被误改，所以本测试采用 Mongo 资源快照而不是只判断返回码。

### 单元测试执行的真实代码与 Mock 边界

`testAddRemoveRegProtectionLegResourceSymmetry` 使用真实本地 MongoDB，并执行真实的：

- `getBindingList()` 候选路径计算；
- `TunnelBinder.doIt()` 加腿分配和数据库写入；
- Tunnel/OCH/SiteLink/PhyLink/PhyNode/XC/InternalLink/Equipment 更新；
- remove-leg marker 状态机；
- 分布式锁资源收集、获锁后重读和引用判断；
- secondary/third 路由裁剪；
- REG L 口、板卡、节点和 SiteNode rack 关系回收；
- TaskInfo 上下文记录。

只 Mock 两个无法在 manager 单元测试中真实完成的设备阶段：

1. `ProtectionLegDeviceRunner` 被替换为空成功执行器，不连接真实网元、不执行 APS/NETCONF；
2. 加腿完成后调用 `stabilizeImplementedAddLeg()`，模拟 implement 模块成功回调，把 OCH/Tunnel 从 `PartialImplement` 收敛到 `Implement` 并清理临时加腿 marker。

所以该用例验证的是 **allocate + MongoDB 资源对称性**，不等价于真实设备下发测试。APS、设备命令和设备超时恢复仍需按《减腿流程说明.md》的手工测试执行。

### 一腿基线如何形成

测试要求从 dump 中的 C3 三腿 Tunnel 开始。初始化阶段循环调用真实 remove-leg：

```text
三腿：primary + secondary + third
    ↓ remove third
两腿：primary + secondary
    ↓ remove secondary
一腿：primary
```

设备执行器虽然被 Mock，但 marker、锁、数据库 trim、共享引用判断和 REG 回收全部真实执行。减到一腿后，对八个 Mongo 集合生成 `oneLegBaseline`。

### REG secondary 对称性

每轮首先测试 REG 位于 secondary 的情况：

```text
oneLegBaseline
    ↓ addOneRegLeg(expectedLegCount=2)
primary + REG secondary
    ↓ 检查 REG 资源数量
    ↓ removeOneLeg()
actualOneLegSnapshot
    ↓ 逐集合比较
actualOneLegSnapshot == oneLegBaseline
```

加腿后立即断言：

- 保护腿数精确增加 1；
- 目标腿存在 EPC-REG 节点；
- 两个 REG L 口对应两条自环 XC；
- 目标腿包含四条方向 OS Link；
- REG 节点包含对应四条 InternalLink。

删除后 `assertResourceSnapshotsEqual()` 比较完整一腿快照。如果任何资源没有恢复，测试会指出发生变化的集合、文档 ID 和第一个字段差异位置。

### REG third 对称性

本地 dump 只有一条可构造 REG 的中间站路径。为了让 REG 落入 third，必须先占用 secondary：

```text
oneLegBaseline
    ↓ addOnePlainLeg(direct path)
primary + plain secondary
    ↓ 保存 twoLegBaseline
    ↓ addOneRegLeg(expectedLegCount=3)
primary + plain secondary + REG third
    ↓ removeOneLeg()（third 优先）
actualTwoLegSnapshot
    ↓ 逐集合比较
actualTwoLegSnapshot == twoLegBaseline
    ↓ removeOneLeg()（删除 plain secondary）
actualOneLegSnapshot == oneLegBaseline
```

`addOnePlainLeg` 只是占位 secondary，目的是覆盖 third 删除分支。真正被验证加减对称的仍然是 REG third。

### 为什么连续执行三轮

单轮恢复快照只能证明一次操作看起来正确。连续三轮用于发现累积问题：

- 第一轮遗留的 Busy L 口导致第二轮换端口；
- XC、OS Link 或 InternalLink 泄漏；
- `binding3rdLeg`、`protection-change-*` marker 残留；
- 空壳 TPC4 板卡或 REG 节点不断累积；
- SiteNode rack 关系重复或未删除；
- 数组顺序或字段状态每轮漂移；
- 第二次操作受到第一次未释放资源影响。

三轮每次都必须回到同一个 `oneLegBaseline` 和对应的 `twoLegBaseline`，任何一轮漂移都会失败。

### 快照如何比较

`snapshotResourceCollections()` 读取八个集合的全部文档并进行语义规范化：

- Map 字段按 key 排序；
- Iterable 内容规范化后排序；
- Mongo/YANG 序列化产生的 absent、`null`、空数组和空对象按等价空值处理；
- 文档整体排序后按集合比较；
- 不忽略资源 ID、TP 属性、频率、速率、连接状态、XC、InternalLink、Equipment 和 rack。

失败信息示例：

```text
secondary REG add/remove cycle=2 resource diff:
config-phy-node expected=..., actual=..., changes=[...]
```

`changes` 会优先显示：

- 缺失文档：`missing <document-id>`；
- 多余文档：`extra <document-id>`；
- 同一文档字段变化：显示首次差异附近的 expected/actual 内容。

### 单独调试加腿与完整对称测试的区别

| 测试方法 | 目的 | 结束时 Mongo 状态 |
|---|---|---|
| `testAddOnePlainLeg` | 单独检查 direct secondary 加腿结果 | 故意保留两腿 |
| `testAddOneRegLeg` | 先加 direct secondary，再检查 REG third 资源分配 | 故意保留三腿 |
| `testAddRemoveRegProtectionLegResourceSymmetry` | 自动验证 REG secondary/third 加减完全对称 | 最终回到一腿 |

前两个用例用于 MongoDB Compass 和路由图手工观察，不能替代完整对称性测试。

## TaskInfo 检查

每次减腿都会捕获并打印完整子 TaskInfo。上下文包含：

- `context-resolved`、`marker-prepared`、`device-deimplemented`、`db-trim-start`、`db-trim-completed`；
- OCH、被删腿、减腿前后腿数、相关 Tunnel、SiteLink、PhyLink 和 XC；
- REG node、L 口、XC、OS Link、板卡各自的 candidate、retained、deleted/released 分类。

单元测试通过专用 `ProtectionLegDeviceRunner` stub 模拟设备侧减腿成功，只跳过真实设备下发；数据库识别、锁、引用判断和资源裁剪仍执行真实代码。这也避免测试环境缺少实现侧类（例如 `ApsSwitchManager`）造成无关的 `ClassNotFoundException`。

## 单独加腿测试（供手工检查 MongoDB）

新增两个可单独执行的测试入口：

- `testAddOnePlainLeg`：把 C3 Tunnel 规整到一腿后，选择 direct path 增加普通 secondary；
- `testAddOneRegLeg`：把 C3 Tunnel 规整到一腿，先增加 direct secondary，再选择带中间站的路径增加 REG third，并校验两个 REG 自环 XC、四条 OS Link 和四条 InternalLink。

这两个测试会模拟“新增腿设备实现成功”后的状态收敛，但不会连接真实设备。`testAddOnePlainLeg` 故意保留两腿，`testAddOneRegLeg` 故意保留 `primary + plain secondary + REG third` 三腿，方便使用 MongoDB Compass 和路由图手工检查；不会自动减回一腿。

每个测试执行前先恢复三腿 dump：

```powershell
& 'C:\app\MongoDB\mongodb-database-tools\bin\mongorestore.exe' `
  --uri='mongodb://localhost:27017' --db=sotn --drop `
  'C:\DCI\server-test\mongo-dump\sotn'
```

普通保护腿：

```powershell
mvn -s settings.xml -q -pl allocate/manager `
  '-Dtest=TunnelBinderDoItTest#testAddOnePlainLeg' test
```

REG 保护腿：

```powershell
mvn -s settings.xml -q -pl allocate/manager `
  '-Dtest=TunnelBinderDoItTest#testAddOneRegLeg' test
```

执行后检查 `config-och-link`、`config-tunnel`、`config-site-link`、`config-phy-link`、`config-phy-node` 和 `config-site-node`。检查完成后重新恢复 dump，避免该两腿状态影响其他测试。

## 通过标准

- 三轮 secondary/third REG 加减循环全部通过；
- 删除同一条腿后，八个资源集合完整回到加腿前快照；
- 原 `testRemoveLeg` 中共享 OCH 的其他 Tunnel 正常腿和客户侧状态不被误改；
- TaskInfo 能定位每个阶段及 REG 资源的保留/删除决定；
- `TunnelBinderDoItTest` 整类无失败、无错误；
- designer、manager、implement Reactor 编译成功；
- 最终 Mongo 恢复结果为 0 failure。
